What the app is

And Breathe is a breathwork app that takes a member through a multi-week programme. Each day has two short guided sessions (morning and evening) built around breath holds, pulse readings and recovery. Each week continues the same programme, building tolerance as it goes. Members log their workouts, watch their progress against themselves, can choose to share their practice with a cohort group, and can join live breathwork sessions and coaching calls.

Who uses it

Person What they do
Member Does the daily sessions, checks in, logs workouts, and joins live calls. Can choose to join their cohort's group and post there. Can be in several programmes and cohorts, or none (solo).
Coach A role inside one cohort. Sees the cohort roster and every member's full data for the dates that member was in the cohort.
Admin A global account type. Creates programmes, breath-hold steps, session times, cohorts and live calls, and assigns coaches.

Using this guide with Claude

This guide is written so you can hand it straight to Claude (or another AI coding assistant) and have it build the app. This page explains what that means and how to do it, step by step.

What Claude does here

Claude is an AI assistant made by Anthropic. You may know it as a chat window that answers questions. It also comes as Claude Code, a version that works inside a project folder on a computer and writes the code itself.

The idea is simple. You give Claude this guide. Claude reads all of it, then builds the app one piece at a time. After each piece it stops and tells you what it did, so a person can try it on a phone before the next piece starts.

Claude can only build what it has been told about, which is why this guide is so detailed. The more of it Claude reads, the less it has to guess.

What to expect

  • It builds in eleven steps. The build plan lists them. Each one ends in something you can open on a phone and try.
  • It stops and reports. After each step Claude summarises what it built and anything it found unclear. Read that, try the app, then tell it to carry on.
  • You can talk to it normally. "The Today screen doesn't match the picture" is a perfectly good instruction.
  • Some things aren't decided yet. They're listed under Assumptions. Claude builds the simplest version of each and flags it, so nothing gets stuck waiting.
  • A person still checks the work. Claude does the typing. Someone needs to try each step and say whether it's right.

Rules for whoever builds it

These apply to a developer and to Claude alike. They're the few things that cause real trouble if ignored.

  • The database is the source of truth. Change it only through a new migration, then regenerate types.
  • Never hand-edit src/types/database.ts.
  • Keep the "Concept · Example data" badges out of the real app. They only mark the mockups.
  • Breath-hold safety copy and timings must come from the course author before release. The seeded values are placeholders.
  • Where this guide says Assumption, build the simplest version and flag it, rather than inventing a rule.

The coach's view

Coaches use the same screens as members. A coach picks a cohort, then a member, and sees that member's Today, Progress and Workouts in read-only mode. No separate coach design exists or is needed for the MVP.

The admin's view

Assumption For the MVP, admins manage programmes, steps, session times, cohorts and live calls directly in the Supabase dashboard. An in-app admin area is a later decision.

Joining the group

Being in a cohort and being in its group are two different things. An admin puts a member in a cohort, which gives their coach access. The member then decides whether to join the group feed, and separately whether to share their check-ins there. Both start off. Automatic sharing is a version 2 idea.

Why membership has dates

A member can leave one cohort and join another, or be in two at once. Each membership stores joined_on and left_on. A coach sees a member's data only for days that fall inside those dates, so a new coach doesn't inherit a member's history from another cohort.

Sign-in with email

How a member gets into the app. They type their email, and we send them a link to tap and a six-digit code to type in, whichever is easier. There's no password to remember, store or reset, and no Google or Apple account needed, which matters when the app is sold to companies. The steps below are what happens behind the scenes.

Why not Google?

The app is likely to be sold to companies later, and not every company uses Google. Email works for everyone and keeps personal Google accounts out of a work tool.

Flow

  1. The member enters their email. The app calls supabase.auth.signInWithOtp({ email }).
  2. Supabase emails a sign-in link and a six-digit code.
  3. Either the member taps the link, which opens the app through a deep link and completes sign-in, or they type the code and the app calls supabase.auth.verifyOtp({ email, token, type: 'email' }).
  4. Supabase creates the user on first sign-in. A database trigger then creates the profile (with an empty name), default settings and a reminder for each session time.
  5. The app sees the empty name and asks "What should we call you?" once.
  6. The session is stored on the phone so the member stays signed in, following Supabase's React Native guide.

Setup checklist

  • Turn on the Email provider in Supabase. Turn off password sign-up.
  • Edit the Magic Link email template so it includes both the link and the code ({{ .Token }}).
  • Connect an email sending service through Supabase's custom SMTP settings before anyone outside the team signs in.
  • Add the app's deep link (for example andbreathe://) to Supabase's allowed redirect URLs, and set the same scheme in the Expo config.
  • Make the first admin by setting profiles.app_role to admin in the Supabase dashboard. Members can never change their own role.

Wearables

How the app gets data from a member's watch. It starts with Apple Watch, the most popular, through Apple Health, the health app built into every iPhone. The data is laid out the way Apple Health lays it out, with plain-English names, so Garmin and others slot in later without changing anything.

Why Apple first

  • Most members will have one. Apple Watch is the most widely worn smartwatch.
  • Apple Health is a hub. Garmin and WHOOP can sync some of their data into it, so some of their users get something from day one.
  • It works on the phone. No server connection or partner approval needed, unlike Garmin.

The MVP is iPhone only, so Apple Health covers everyone. Android (with Google's Health Connect), Garmin and WHOOP come in MVP 2, as new sources in the same tables.

How it works

  1. In Settings, the member taps Connect Apple Health. iPhone shows its own permission screen listing what the app wants to read.
  2. Each time the app opens, it asks Apple Health for anything new since health_connections.last_synced_at.
  3. It saves each new record with Apple's record id in source_record_id, so syncing twice never doubles anything.
  4. Progress, Workouts and the guided session's pulse steps read from these tables. The member can still type numbers in by hand.

What we read

Measurement Apple Health name Stored as Used for
Heart rate HKQuantityTypeIdentifierHeartRate health_readings, heart_rate, bpm Filling in starting and finishing pulse
Resting heart rate HKQuantityTypeIdentifierRestingHeartRate health_readings, resting_heart_rate, bpm The resting pulse chart on Progress
Heart rate variability HKQuantityTypeIdentifierHeartRateVariabilitySDNN health_readings, heart_rate_variability_sdnn, ms Recovery trend on Progress
Breathing rate HKQuantityTypeIdentifierRespiratoryRate health_readings, respiratory_rate, breaths_per_minute Overnight breathing trend
Blood oxygen HKQuantityTypeIdentifierOxygenSaturation health_readings, oxygen_saturation, percent Stored for later. Not shown in version 1.
Sleep HKCategoryTypeIdentifierSleepAnalysis sleep_periods, one row per stage Suggesting the sleep answer at check-in
Workouts HKWorkoutType workouts with source = 'apple_health' The workout log, without typing

Apple workout types map to ours: running to run, cycling to cycle, strength training to strength, anything else to other. Members can change a workout to hyrox afterwards.

Rules for the data

  • Apple's layout, our names. Readings, sleep and workouts are kept the way Apple Health keeps them, but named in plain English, following the Activatus code standards.
  • Every row says where it came from. source is apple_health or manual. Garmin and WHOOP get added to that list when they're connected.
  • Heart rate variability comes in two kinds. Apple measures SDNN. Garmin and WHOOP measure RMSSD, a different number. They are never mixed: each gets its own reading type, so a member's trend doesn't jump when they change watch.
  • No double counting. When Garmin arrives, a Garmin user may have the same workout from Garmin directly and from Apple Health. The app keeps the direct one and ignores the copy.

Setup checklist

  • Install the HealthKit library and its Expo config plugin, and switch from Expo Go to a custom development build.
  • Turn on the HealthKit capability for the app in the Apple Developer account.
  • Write the two iPhone permission messages (why the app reads health data, and that it doesn't write any) in plain, calm language.
  • Publish a privacy policy that covers health data before submitting to the App Store. Apple checks this closely for health apps.

Database overview

The database is where everything the app remembers is kept: who the members are, which sessions they've done, what they've posted. Think of it as a set of linked spreadsheets. There are twenty-two of them in six areas: twenty-one tables and one read-only view.

Areas

How it fits together

session_slots ── used by protocol_steps, sessions, session_reminders
programs ─┬─ program_blocks
          ├─ protocol_steps
          ├─ cohorts ─┬─ cohort_members ── profiles
          │           └─ live_calls
          └─ enrolments ── sessions ─┬─ session_holds
                                     └─ check_ins
profiles ─┬─ user_settings
          ├─ session_reminders
          ├─ workouts
          ├─ health_connections
          ├─ health_readings
          └─ sleep_periods
cohorts ── group_posts ─┬─ group_comments
                        └─ group_cheers

Principles

  • Worked out, not stored: current week, "Up next" and Progress averages are calculated from dates and sessions.
  • One exception: sessions.base_score is stored, but only ever written by the database from the holds, so reads are fast and the formula lives in one place.
  • Lists that may grow are tables, not fixed lists. Session times live in session_slots so an admin can add noon or night later without a developer.
  • Deleting a person removes everything they own in one step.

Tables

A table is like one sheet in a spreadsheet. Each row is one thing (a member, a session, a post) and each column is one fact about it. This page lists every table, what it's for, who can access it, and its columns. A key marks the primary key, the column that tells one row from another, and link marks a column that points to another table.

Fixed value lists

Some answers only ever come from a short, fixed list. Mood, for example, is always low, flat, okay, good or great. Keeping these lists in the database means the app can never save a value that isn't on one. Developers call them Postgres enums. They become TypeScript union types automatically.

All lists

Name Values Used by
app_role member, admin profiles
cohort_role member, coach cohort_members
session_status pending, in_progress, done, skipped sessions
mood low, flat, okay, good, great check_ins
sleep_quality poor, fair, good, great check_ins
workout_type hyrox, run, strength, cycle, other workouts
post_kind manual, check_in group_posts
protocol_step_type pulse, base, hold, recovery protocol_steps
enrolment_status active, completed, left enrolments

Session times (morning, evening) are not on this list. They live in the session_slots table so they can be added to without a developer.

Functions and triggers

Small jobs the database does by itself, so the app never has to remember to. A trigger runs automatically when something happens, such as a session being finished. A function is a job the app can ask for by name.

Triggers

When What happens
A new user signs in for the first time Creates their profile (name left empty for the app to ask), default settings and a reminder for each session time
A hold is added, changed or removed Recalculates sessions.base_score
A session changes to done Posts a check-in to each cohort group the member has joined with sharing on, for that session's programme
A member edits their cohort membership Allows only joining or leaving the group, the sharing toggle, and leaving the cohort. Everything else needs an admin.
Profiles, settings or posts are updated Stamps updated_at

Functions the app can call

Function Returns
cohort_member_count(cohort_id) Number of members in the group, for "6 members"
calculate_base_score(session_id) The base score. For now, the best hold in seconds.
get_progress_summary(…) To build Week 1 against this week averages for Progress

Base score

A placeholder formula until the course author supplies the real one. Changing it means replacing calculate_base_score in a new migration, then running a one-off update to recalculate past sessions. The app needs no change.

A rating scale (300 seconds, five minutes, as "Amazing") is noted for later and not built.

Types and testing

Two safety nets. Types tell the code exactly what shape each piece of information is, so mistakes are caught while the app is being written and not on a member's phone. Tests are automatic checks that the privacy rules still hold after every change.

Scripts

Command Does
pnpm db:start Starts Supabase locally
pnpm db:reset Rebuilds the local database from migrations and seed data
pnpm db:test Runs the database tests
pnpm db:types Generates src/types/database.ts from the local database
pnpm db:types:check Fails if the generated types are out of date. Run it in CI.

Using the types

import type { SessionType, MoodType } from '@/types/databaseTypes'
import { supabase } from '@/lib/supabase'

const { data } = await supabase
  .from('sessions')
  .select('*, session_holds(*)')
  .eq('session_date', today)
// data is fully typed from the database

Database tests

  • Base score equals the best hold.
  • New users get one reminder per active session time (two to start).
  • A member can't read another member's workouts.
  • A member can't list other members of a cohort.
  • A member who hasn't joined the group can't read the feed, and group members can't see their name.
  • Finishing a session posts to the group only when the member has joined and sharing is on.
  • A member can read live calls for their cohort and open calls, but not other cohorts' calls.

Add a test for every new access rule.

Deploy and Live

Deploy is where you test the user flows on your own iPhone and confirm you're happy with the final product. Nothing is released to the App Store until you approve it. Live means the app is in the store and maintained over time.

User acceptance testing: you try it

  1. After each feature you get a test version on your iPhone through TestFlight.
  2. It comes with a short list of user flow checks, such as "Sign in with a new email and check you land on Today with two reminders". Each check says exactly what you should see.
  3. You mark each one pass, fail or skip, within five working days.
  4. Anything that fails is fixed, and you check it again.

Release

  1. App icon, splash screen, store listing, screenshots and privacy details.
  2. You approve the release.
  3. We submit to the App Store. Apple reviews health apps closely, so allow a few days.
  4. Once approved, we check the live version works. That's Live.
