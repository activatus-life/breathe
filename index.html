What the app is

And Breathe is a breathwork app that takes a member through a multi-week programme. Each day has two short guided sessions (morning and evening) built around breath holds, pulse readings and recovery. Each week continues the same programme, building tolerance as it goes. Members log their workouts, watch their progress against themselves, can choose to share their practice with a cohort group, and can join live breathwork sessions and coaching calls.

Who uses it

PersonWhat they do
MemberDoes the daily sessions, checks in, logs workouts, and joins live calls. Can choose to join their cohort's group and post there. Can be in several programmes and cohorts, or none (solo).
CoachA role inside one cohort. Sees the cohort roster and every member's full data for the dates that member was in the cohort.
AdminA global account type. Creates programmes, breath-hold steps, session times, cohorts and live calls, and assigns coaches.

The coach's view

Coaches use the same screens as members. A coach picks a cohort, then a member, and sees that member's Today, Progress and Workouts in read-only mode. No separate coach design exists or is needed for the MVP.

The admin's view

Assumption For the MVP, admins manage programmes, steps, session times, cohorts and live calls directly in the Supabase dashboard. An in-app admin area is a later decision.

Joining the group

Being in a cohort and being in its group are two different things. An admin puts a member in a cohort, which gives their coach access. The member then decides whether to join the group feed, and separately whether to share their check-ins there. Both start off. Automatic sharing is a version 2 idea.

Why membership has dates

A member can leave one cohort and join another, or be in two at once. Each membership stores joined_on and left_on. A coach sees a member's data only for days that fall inside those dates, so a new coach doesn't inherit a member's history from another cohort.

Sign-in with email

How a member gets into the app. They type their email, and we send them a link to tap and a six-digit code to type in, whichever is easier. There's no password to remember, store or reset, and no Google or Apple account needed, which matters when the app is sold to companies. The steps below are what happens behind the scenes.

Why not Google?

The app is likely to be sold to companies later, and not every company uses Google. Email works for everyone and keeps personal Google accounts out of a work tool.

Flow

  1. The member enters their email. The app calls supabase.auth.signInWithOtp({ email }).
  2. Supabase emails a sign-in link and a six-digit code.
  3. Either the member taps the link, which opens the app through a deep link and completes sign-in, or they type the code and the app calls supabase.auth.verifyOtp({ email, token, type: 'email' }).
  4. Supabase creates the user on first sign-in. A database trigger then creates the profile (with an empty name), default settings and a reminder for each session time.
  5. The app sees the empty name and asks "What should we call you?" once.
  6. The session is stored on the phone so the member stays signed in, following Supabase's React Native guide.

Setup checklist

  • Turn on the Email provider in Supabase. Turn off password sign-up.
  • Edit the Magic Link email template so it includes both the link and the code ({{ .Token }}).
  • Connect an email sending service through Supabase's custom SMTP settings before anyone outside the team signs in.
  • Add the app's deep link (for example andbreathe://) to Supabase's allowed redirect URLs, and set the same scheme in the Expo config.
  • Make the first admin by setting profiles.app_role to admin in the Supabase dashboard. Members can never change their own role.

Wearables

How the app gets data from a member's watch. It starts with Apple Watch, the most popular, through Apple Health, the health app built into every iPhone. The data is laid out the way Apple Health lays it out, with plain-English names, so Garmin and others slot in later without changing anything.

Why Apple first

  • Most members will have one. Apple Watch is the most widely worn smartwatch.
  • Apple Health is a hub. Garmin and WHOOP can sync some of their data into it, so some of their users get something from day one.
  • It works on the phone. No server connection or partner approval needed, unlike Garmin.

Apple Health is iPhone only. Android members type their numbers in until Google's Health Connect is added. Garmin comes next, as a direct connection.

How it works

  1. In Settings, the member taps Connect Apple Health. iPhone shows its own permission screen listing what the app wants to read.
  2. Each time the app opens, it asks Apple Health for anything new since health_connections.last_synced_at.
  3. It saves each new record with Apple's record id in source_record_id, so syncing twice never doubles anything.
  4. Progress, Workouts and the guided session's pulse steps read from these tables. The member can still type numbers in by hand.

Rules for the data

  • Apple's layout, our names. Readings, sleep and workouts are kept the way Apple Health keeps them, but named in plain English, following the Activatus code standards.
  • Every row says where it came from. source is apple_health or manual. Garmin and WHOOP get added to that list when they're connected.
  • Heart rate variability comes in two kinds. Apple measures SDNN. Garmin and WHOOP measure RMSSD, a different number. They are never mixed: each gets its own reading type, so a member's trend doesn't jump when they change watch.
  • No double counting. When Garmin arrives, a Garmin user may have the same workout from Garmin directly and from Apple Health. The app keeps the direct one and ignores the copy.

Setup checklist

  • Install the HealthKit library and its Expo config plugin, and switch from Expo Go to a custom development build.
  • Turn on the HealthKit capability for the app in the Apple Developer account.
  • Write the two iPhone permission messages (why the app reads health data, and that it doesn't write any) in plain, calm language.
  • Publish a privacy policy that covers health data before submitting to the App Store. Apple checks this closely for health apps.

The database is where everything the app remembers is kept: who the members are, which sessions they've done, what they've posted. Think of it as a set of linked spreadsheets. There are twenty-two of them in six areas: twenty-one tables and one read-only view.

Principles

  • Worked out, not stored: current week, "Up next" and Progress averages are calculated from dates and sessions.
  • One exception: sessions.base_score is stored, but only ever written by the database from the holds, so reads are fast and the formula lives in one place.
  • Lists that may grow are tables, not fixed lists. Session times live in session_slots so an admin can add noon or night later without a developer.
  • Deleting a person removes everything they own in one step.

returns boolean
language sql stable security definer set search_path = ''
as $$

    where id = auth.uid() and app_role = 'admin'

$$;

returns boolean
language sql stable security definer set search_path = ''
as $$
  select exists (
    select 1 from public.cohort_members
    where cohort_id = target_cohort_id
      and user_id = auth.uid()
      and left_on is null
  );
$$;

-- In the cohort and has joined its group feed. Coaches are always in the group.
create function public.is_group_member(target_cohort_id uuid)
returns boolean
language sql stable security definer set search_path = ''
as $$
  select exists (
    select 1 from public.cohort_members
    where cohort_id = target_cohort_id
      and user_id = auth.uid()
      and left_on is null
      and (in_group or role = 'coach')
  );
$$;

create function public.is_cohort_coach(target_cohort_id uuid)
returns boolean
language sql stable security definer set search_path = ''
as $$
  select exists (
    select 1 from public.cohort_members
    where cohort_id = target_cohort_id
      and user_id = auth.uid()
      and role = 'coach'
      and left_on is null
  );
$$;

-- A coach sees a member's data only for dates the member was in the coach's cohort.
create function public.coach_can_view_member(member_id uuid, on_date date)
returns boolean
language sql stable security definer set search_path = ''
as $$
  select exists (
    select 1
    from public.cohort_members as coach
    join public.cohort_members as member on member.cohort_id = coach.cohort_id
    where coach.user_id = auth.uid()
      and coach.role = 'coach'
      and coach.left_on is null
      and member.user_id = member_id
      and member.role = 'member'
      and on_date >= member.joined_on
      and (member.left_on is null or on_date <= member.left_on)
  );
$$;

-- True when the caller and another person are both currently in the same cohort group.
create function public.shares_active_cohort(other_user_id uuid)
returns boolean
language sql stable security definer set search_path = ''
as $$
  select exists (
    select 1
    from public.cohort_members as mine
    join public.cohort_members as theirs on theirs.cohort_id = mine.cohort_id
    where mine.user_id = auth.uid()
      and mine.left_on is null
      and (mine.in_group or mine.role = 'coach')
      and theirs.user_id = other_user_id
      and theirs.left_on is null
      and (theirs.in_group or theirs.role = 'coach')
  );
$$;

-- Lets members show "6 members" in the group without being able to list who they are.
create function public.cohort_member_count(target_cohort_id uuid)
returns integer
language sql stable security definer set search_path = ''
as $$
  select case
    when public.is_active_cohort_member(target_cohort_id) or public.is_admin() then (
      select count(*)::integer from public.cohort_members
      where cohort_id = target_cohort_id and role = 'member' and in_group and left_on is null
    )
  end;
$$;

returns integer
language sql stable set search_path = ''
as $$
  select max(duration_seconds) from public.session_holds
  where session_id = target_session_id;
$$;

  affected_session_id uuid := coalesce(new.session_id, old.session_id);

-- When a session is finished, post "<slot> done" to every cohort group the member
-- has joined and shares with, for the programme that session belongs to.
create function public.post_check_in_on_session_done()
returns trigger
language plpgsql security definer set search_path = ''
as $$
begin
  if new.status <> 'done' or old.status = 'done' then
    return new;
  end if;

  insert into public.group_posts (cohort_id, author_id, post_kind, session_id)
  select membership.cohort_id, new.user_id, 'check_in', new.id
  from public.cohort_members as membership
  join public.cohorts as cohort on cohort.id = membership.cohort_id
  join public.enrolments as enrolment on enrolment.id = new.enrolment_id
  where membership.user_id = new.user_id
    and membership.role = 'member'
    and membership.left_on is null
    and membership.in_group
    and membership.share_to_group
    and cohort.program_id = enrolment.program_id;

  return new;
end;
$$;

  after update of status on public.sessions
  for each row execute function public.post_check_in_on_session_done();

-- Members may only join or leave the group, change their sharing toggle, or leave the
-- cohort. Everything else is admin-only.
create function public.guard_cohort_member_changes()
returns trigger
language plpgsql set search_path = ''
as $$
begin
  if public.is_admin() then
    return new;
  end if;

  if new.cohort_id <> old.cohort_id
    or new.user_id <> old.user_id
    or new.role <> old.role
    or new.joined_on <> old.joined_on then
    raise exception 'Only an admin can change cohort membership details';
  end if;

  return new;
end;
$$;

create trigger cohort_members_guard before update on public.cohort_members
  for each row execute function public.guard_cohort_member_changes();

  -- The record's id in its source, so syncing again never saves it twice.
  source_record_id text,
  device_name text,
  created_at timestamptz not null default now(),
  check (ended_at >= started_at),
  unique (user_id, source, source_record_id)
